## 〇、排序规则

顺序不是凭手感，按下面五条依次判定，前一条能分出先后就不用看下一条：

1. **依赖优先**：被别的任务依赖的排前面。这条是硬约束，脚本会查——依赖的批次必须早于本任务，违反直接报错。
2. **闭环优先**：不做就会让已经做好的功能显得“半截”的，插到最前面。典型是评论输入框：后端能存能读，但用户发不了。
3. **风险优先**：成本低、出事代价高的（安全、数据正确性），插在功能批次之间的空档做，不占主线。
4. **展示优先**：演示路径上的排在内部优化前面。导航和地图比“索引异步重建”更值得先做。
5. **收尾最后**：只有全部完成才能做的（一键启动、演示材料），固定放最后一批。

批次只是**顺序的载体**，不是日期承诺。同一批内的任务可以任意顺序做，但跨批必须按编号从小到大。

## 三、明确不做（记录在此，避免反复讨论）

| 项 | 原因 |
|---|---|
| AI / LLM 相关 | 用户另有 LangChain agent 项目 |
| 室内导航、逐转向导航 | 超出「地点 + 路线」的范围 |
| 微信 / 支付 / 专栏 / 小程序 | 与产品定位无关 |
| 刷新令牌、多设备会话管理 | 7 天绝对有效期足够，成本不划算 |

## 四、待观察（有触发条件才做，不进批次）

| 项 | 触发条件 | 做法 |
|---|---|---|
| 搜索降级加熔断 / 限流 | 帖子 > 10 万，或搜索 QPS 到几十，MySQL LIKE 开始吃连接 | 降级层加超时 + 并发上限；ES 连续失败后 30s 内跳过；热门查询缓存 |
| readiness / liveness 分组 | 真要上 K8s | health 分 `db,redis` 与 `ping` 两组 |
| 搜索降级指标 | 部署后想看见“现在走哪条路” | 一个永远 UP、带 `mode` 与降级次数的 HealthIndicator |
| 全量重建索引异步化 | 帖子量上来后启动变慢 | 启动后异步分批重建，不阻塞 ready |

## 五、维护约定

1. **开工前**先把对应行改成 🚧，并确认设计文档已存在（没有就先写）；
2. **完成后**把状态改 ✅，验收列写清“哪条测试 / 哪张截图”，不写“已完成”这种空话；
3. **新增任务**必须写清批次和依赖，没进表的活不开工；
4. 细节不进这张表——表里只留一句话做法，展开写域设计；
5. 域设计**不写状态**，只留一行指回本表；
6. 收工前跑 `node scripts/check-docs.mjs`：验收要具体、测试类要存在、域设计要被引用、**依赖的批次必须早于本任务**。
